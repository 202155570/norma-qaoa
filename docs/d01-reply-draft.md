## 요약

12개 후보에서 6개를 선택하는 PoC는 **지금 동작합니다.** 컨테이너로 납품할 준비도 됐습니다.

다만 솔직하게 함께 적어야 할 것이 있습니다. **이 규모에서는 양자가 고전 전수계산보다 느립니다.**
462가지를 전부 세는 데 80 ms면 끝나고 그건 최적해를 보장하는 반면, QAOA는 5~7초가 걸리고
보장하지 않습니다. 지금 단계는 성능 비교가 아니라 **계측**으로 보는 것이 정확합니다 —
전수계산이 불가능해지는 규모로 가기 전에, 알고리즘이 실제로 무엇을 하는지 작은 문제에서
정확히 재 두는 작업입니다.

## ① 12개 후보·6개 선택 지원 가능 여부

**가능합니다.** `[측정]`

| | |
|---|---|
| 큐비트 | 12 (자산 1개 = 큐비트 1개) |
| 가해 조합 | 462 (`SYN_03` 필수 포함이므로 C(11,5)) |
| 결과 | `status = SUCCEEDED`, 후보 5개 (요청 `top_k = 5`) |
| 최적 후보 | `SYN_01 · 03 · 05 · 07 · 08 · 10`, `objective_base = −0.135053` |

최적 후보는 462가지 중 1등이 맞습니다 — 고전 전수계산과 대조해 확인했습니다.
다만 **QAOA가 항상 1등을 뽑는다는 뜻은 아닙니다.** 이 입력·이 시드에서 그랬다는 뜻입니다.

현재 코드의 자산 수 상한은 **16**입니다 (`MAX_ASSETS`). 스펙 20쪽 단계 F의 "N≤16 확대"까지는
코드 변경 없이 받을 수 있고, 그 이상은 아래 ⑤와 별도 문서(`docs/scaling-plan.md`)를 봐 주세요.

| | 실시간 | CPU 시간 | 비고 |

| QAOA 1건 (다른 작업 병행) | 5.5 – 6.6 s | 21 – 22 s | Aer가 멀티스레드로 돕니다 |

> **실시간이 3배 넘게 흔들립니다.** 같은 머신에서 다른 작업이 돌고 있었는지에 따라 달라집니다.
> 운영 환경에서 쓸 숫자가 필요하면 **전용 환경에서 다시 재야 합니다.** 지금 값은 개발 머신 기준입니다.

메모리는 이 규모에서 문제가 되지 않습니다 (상태벡터 64 KB).

확정값을 드리겠습니다. 현재 시뮬레이터는 **CPU만 사용합니다.**

## ③ 권장 알고리즘과 설정

알고리즘은 **QAOA**로 유지하기를 권합니다. 다만 **스펙 11쪽 예시의 실행 설정 네 가지는
바꾸기를 권합니다.** 전부 측정 근거가 있습니다.

| 항목 | 스펙 예시 | 권장 | 근거 `[측정]` |
|---|---|---|---|
| `depth` | 1 | **4 ~ 5** | p=1에서는 회로가 사실상 탐색을 하지 않습니다. 이득이 거의 전부 "제약을 지키게 만드는" 몫이고 가해 영역 안에서는 분포가 균등에 가깝습니다. 진짜 탐색은 **p=4에서 켜집니다** |
| `max_starts` | 1 (코드도 1로 고정) | **상한 완화** | 재시작 1회로는 최적점을 못 찾습니다. 202회로 늘리니 성능이 3.29배 → 3.87배로 올라갔습니다. 한계는 회로 깊이가 아니라 **파라미터 탐색 예산**이었습니다 |
| `max_objective_evaluations` | 60 | **상향 또는 `grid_size` 하향** | 60 중 49를 그리드가, 1을 최종 샘플링이 먼저 쓰므로 COBYLA에 10회만 남습니다 |
| `penalties` | 4.0 | **0.3 ~ 0.5** | 가해 462개 전부를 비가해보다 위에 두는 데 필요한 최소값이 **0.2839**입니다. 4.0은 그 **14배**이고, 과한 벌점이 모든 자산 쌍의 결합을 0.9914~1.0000으로 뭉치게 해 탐색 성능을 떨어뜨립니다 |

> `depth > 1`은 현재 엔진 설정 플래그(`allow_depth_gt_1`)가 꺼져 있어 거부됩니다.
> **`[결정 필요] D03`의 깊이 승인이 있어야 켭니다.**

측정 상세는 `docs/proposals.md`와 측정 보고서에 있습니다.

## ④ API 또는 컨테이너 제공 여부

**컨테이너 배치로 제안합니다.** 스펙 5쪽이 대안으로 적어 둔 경로입니다.

이유는 세 가지입니다.

1. **입출력 계약이 이미 맞습니다.** 응답 문서의 최상위 필드가 스펙 12쪽 예시와 정확히 일치합니다
   (누락·추가 0). 서버를 붙이지 않아도 단계 B·C를 지금 시작할 수 있습니다.
2. **실행 환경·자원을 엠버스가 통제합니다.** D03이 미결인 상태에서 노르마가 가동률과 응답시간을
   떠안는 것보다, 배치로 시작해 사용량을 보고 정하는 편이 양쪽 모두 위험이 작습니다.
3. **나중에 API로 전환할 때 버릴 것이 없습니다.** 입출력 JSON이 같으므로 HTTP 계층만 얹으면 됩니다.

납품물 (`docs/io-contract.md`, `docs/container-operations.md` 참조):

```
Dockerfile · docker/entrypoint.py · .dockerignore · scripts/build_image.sh
docs/schema/{request,result}.schema.json      기계 판독 스키마
docs/io-contract.md                           필드 의미·단위·검증 규칙
docs/container-operations.md                  한도·취소·재시도·오류 처리
```

실행은 작업 1건당 컨테이너 1회입니다.

```bash
docker run --rm -v ./job:/in:ro -v ./out:/out norma-qaoa:0.1.0
```

이미지에 자체 점검이 들어 있어 `docker run --rm norma-qaoa:0.1.0 --selftest` 한 줄로 검증됩니다.

> ⚠️ **이미지는 아직 빌드된 적이 없습니다.** 작성 환경에 Docker가 없었습니다. 검증한 것은
> 엔트리포인트 로직(로컬 실행), Dockerfile 정적 점검, 스키마, 테스트 167개입니다.
> **첫 빌드에서 오류가 날 수 있습니다.** 나오면 바로 전달해 주시면 고치겠습니다.

**컨테이너에 없는 것**: 작업 취소 API, 멱등 키, 월·일 사용량 한도.
컨테이너는 자기가 몇 번째 실행인지 모르므로 **사용량 집계와 한도는 엠버스 스케줄러가 걸어야 합니다.**
대체 수단은 운영 가이드 2절에 적었습니다.

## ⑤ 실행 기록의 범위

작업마다 `manifest.json`을 남깁니다. 스펙 19쪽 목록 대비 현황입니다. `[측정]`

**기록됩니다**: `request_id` / `job_id` / `attempt_id` / `snapshot_id` / `model_version` /
`input_hash` / `qubo_hash` / `circuit_hash` / `backend_circuit_hash` / 컨테이너 digest /
backend / 시드 5종 전부 / `qubits` / `depth` / `evaluations` / `circuits` / `shots` /
실행시간 / 대기시간 / 자원 사용량 / `stop_reason` / 후보 출처 / 후처리 이력 /
라이브러리 버전 7종 / 최적화 추적 / 원표본 전체(`final_counts`) / 벌점 점검 / 경고

**기록되지 않습니다**:

| 항목 | 사유 |
|---|---|
| GPU 사용량 | 시뮬레이터가 CPU로 돕니다. 항상 `null`이며 0으로 적지 않습니다 |
| 승인·발행 버전 | 고객 노출 승인은 엠버스 절차이므로 엠버스가 기록해야 합니다 |
| 취소된 실행의 사용량 | 컨테이너를 중단하면 manifest가 남지 않습니다. 실사용량 보존이 필요하면 호출자가 시작·종료 시각을 기록해야 합니다 |

`max_rss_bytes`는 **프로세스 전체의 최고점**이지 작업 1건만의 값이 아닙니다 (OS가 구간값을 주지 않습니다).
`queue_wait_ms`는 호출자가 `NORMA_ACCEPTED_AT`으로 수락 시각을 넘겨야 의미가 있습니다.

**재현성의 범위**: 같은 시드·같은 입력이 모든 환경에서 같은 표본을 보장하지 **않습니다**.
라이브러리·설정 버전을 함께 보존하는 것까지가 제공 범위이고, 결정적 수치 재검산과
확률적 실행 결과는 구분해 기록합니다.

## 함께 올리는 제안

### 가. 벌점 값을 단계 A에서 함께 정해 주세요

스펙 21쪽 D04(계산 모델 공동 확정)에 해당합니다. 현재 `4.0`은 필요량의 14배이고, 이것이
알고리즘 성능을 직접 떨어뜨립니다. **한 줄 변경이고 제약 강제력은 전혀 손해 보지 않습니다.**

### 나. 단계 C의 성공 기준을 "최적해 일치"가 아니라 "재검산 일치 + 기록 완전성"으로

이 규모에서 양자가 고전을 못 이기므로, 단계 C를 성능으로 판정하면 반드시 실패합니다.
대신 **엠버스 재검산 값이 `objective_penalized`와 일치하는가**, **manifest가 추적에 충분한가**로
판정하기를 제안합니다. 성능 판단은 규모를 올린 뒤 단계 F에서 하는 것이 맞습니다.

### 다. 재검산 시 `risk_scale`을 빠뜨리지 마세요

공분산은 `risk_scale`로 **나눈 뒤** 쓰입니다 (`C = covariance_annual / risk_scale`).
이 나눗셈을 빼면 모든 후보에서 값이 어긋납니다. `docs/io-contract.md`에 공식과 검산 예시를 적었습니다.
계약 테스트에서 가장 먼저 어긋날 지점이라 미리 알려 드립니다.
